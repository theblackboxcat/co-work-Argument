# 夜间执行规范（必读，否则会白跑）

日期：2026-10-05

---

## 0. 昨晚的教训（必须避免重演）

2026-10-04 夜间：接近一半的服务器**没有产出任何结果**，只留下一句
「我会在后台运行，明天早上给你结果」。

**后台任务在对话结束后会被清除。** 那些服务器实际上什么都没做，
但看起来像"已经在跑了"。

这不是能力问题，是**执行方式问题**。本节规定的就是防这个。

---

## 1. 三条硬规则

### 规则一：前台运行，不许承诺后台

在目标服务器上，实验必须**在前台阻塞运行**，直到跑完或明确失败。

**禁止**这样做：

> ✗「我现在启动 X，预计需要 2 小时，明天早上给你结果。」
> ✗「我会在后台运行这批任务，请稍等。」
> ✗「已提交到后台队列，稍后汇报。」

**必须**这样做：

> ✓ 用前台阻塞命令跑，输出直接打屏（或 `tee` 到日志）。
> ✓ 命令返回前不要结束对话、不要给"稍后汇报"的承诺。

如果单片预计超过 ~20 分钟，**切成更小的片**（改 `--n-slices`），
让每片能在前台跑完。例如 E8 每片 10.6 h，就该切到 40+ 片。

### 规则二：必须看到可验证的产出才算完成

每片跑完后，**当场**确认这三件事，并把输出贴进对话：

```bash
# 1. 行数对得上
wc -l results/E10_slice03.jsonl
#    期望：spec 里的 jobs 数（续跑时是剩余数）

# 2. 无 error 记录
grep -c '"error"' results/E10_slice03.jsonl   # 期望：0

# 3. 实际内容合理（acc 在 0~1，不是全 0 或全 1）
head -1 results/E10_slice03.jsonl
```

**如果做不到这三步，就是没做完。** 不要报告"已完成"。

### 规则三：跑完立刻验证，不要只报告进度

对话结束时必须有：跑了多少条、多少小时、有无 error、文件多大。
**"正在跑"不是交付，"文件在这里且验证通过"才是交付。**

## 2. 夜间排程建议

### 2.1 每台的片数上限

按实测单 run 耗时（105–157 s，4 workers）：

| 单片代价 | 前台能跑完吗 | 每台建议片数 |
|---|---|---|
| ≤ 1 h | 稳 | 6–8 |
| 1–3 h | 可以 | 3–4 |
| 3–6 h | 勉强 | 1–2 |
| > 6 h | **不行** | 必须再切 |

**E8 的原始切法每片 10.6 h，必须重切。** 用：
```bash
python make_slices.py --experiment E8 --n-slices 48
```
得到每片约 2.6 h。

### 2.2 夜间的实际排法（3 台机器）

```
18:00-19:00 拷分发包、pip 装torch、跑 make_slices 确认片数
19:00-23:00 前台跑第一轮（E4 全部 + E6 前半）
23:00-03:00 前台跑第二轮（E6 后半 + E10 全部）
03:00-06:00 前台跑第三轮（E1 若干片）
06:00-07:00 merge + 验证，报告结果
```

每轮结束**当场** merge 一次并验证，不要攒到最后。

### 2.3 更好的做法：缩小单片

如果服务器允许长时间前台挂着，切更多片更安全：

```bash
python make_slices.py --n-slices 40     # E4/E6/E10 每片约 0.3-0.5 h
```

40 片 × 3 台 ≈ 每台 13 片 × 0.4 h ≈ 5.2 h，夜里从容跑完。

## 4. 验收清单（猫猫 早上只做这个）

拿到每台服务器的汇报后，逐条核对：

- [ ] 汇报里有实际 jobs 数，不是"约""预计"

- [ ] error 计数为 0
- [ ] 文件已传回
- [ ] 跑完后当场 merge 过并报出覆盖情况

**只要有一条对不上，那台机器就是没产出。** 重新发片。

```bash

python merge_slices.py --exp E10 \
    --inputs "results/E10_slice*.jsonl" --verify
```

会报"应有 300，实得 X，缺 Y"。**只有 Y=0 才算这批完成。**

## 5. 防止半途而废的机制

### 5.1 断点续跑本身就是保障

`run_slice.py` 自动跳过已完成的格点。所以即使一片跑了 80% 被杀，
重跑同一条命令只补剩下的 20%。**不要因为担心失败就不敢重跑。**

### 5.2 分片不要太大

一片越大，夜间半途而废的损失越大。宁可多切。
**单片 ≤ 1 h 是安全线。**

### 5.3 先跑便宜的

E4（90 jobs）→ E6（270）→ E10（300）→ E1（840）→ E8（700*）。
就算夜里只跑完前三项，也拿到了 660 个数据点。

## 6. 今天的编码变更（重要）

codex 的 `S1_FINAL.md` 证明**固定 id slot 的方案是错的**：

固定同一表面（en）、同一数据、同一种子，只改 id 块位置，
n=4000 的准确率在 0.1675–1.0000 之间变，方差比 1.04——
这是**初始化运气**，不是符号身份效应。

本包已全部改成**6×6 循环拉丁方**（`latin.py`）：

```
seed s, surface i  ->  id 块 slot = (i + s) mod n_surfaces
```

每个表面在所有种子上恰好遍历全部 slot，表面主效应与 slot 主效应可分离。

**配平前提：seed 数 ≥ 表面数。** 已核对：

| 实验 | 表面数 | 种子数 | 状态 |
|---|---|---|---|
| E4 | 3 | 6 | OK |
| E6 | 3 | 6 | OK |
| E10 | 2 | 6 | OK |
| E8 | 7 | **7** | OK（原为 4，已改） |
| E1 | 7 | **7** | OK（原为 6，已改） |

E8 和 E1 的种子数是这次为此专门提的。若用原来的 4/6 seeds，
表面主效应会与 slot 噪声纠缠，等于重犯 codex 发现的错。

### E4 不需要改

E4 的"表面"其实是**基质变换**（root_swap / chain_reverse / null_renaming），
训练与测试**共用同一个 `en` 表面**，从不跨语言表面比较——
与 §7.3 迁移、深度扫描同理，固定 slot 对它无害。

已实测确认 E4 的三个变换中，`root_swap` 与 `chain_reverse` 的 token 串
与训练完全相同（因为自变量是 `pools`，token 串本就不该变），
`null_renaming` 才换实体标签。**这正是 E4 的设计意图**：
只改 pools，不动 token。若token 也变了，就不是"只改 pools"了。

## 7. 一个必须交代的容量差异

`latin.build_vocab` 只编码该实验**实际用到的表面**，故 vocab 随表面数变：

| 实验 | 表面数 | vocab | embedding 参数量 |
|---|---|---|---|
| 论文 A1 | 1（`build_vocab`） | 31 | 3,968 |
| E10 | 2（en, relperm） | 59 | 7,552 |
| E6 | 3（en, relperm, entperm） | 87 | 11,136 |
| E8 / E1 | 7 | 197 | 25,216 |

E10 的 embedding 比论文 A1 多 3,584 参数（占总量 0.6%）。
按论文 §5.1「算力混淆」的原则，这**必须在报告里显式说明**：
E10 与论文基线的容量不完全可比。

但 E10 的内部比较（同一条曲线上的五档）vocab 恒定，
**不影响 U 形判读**。受影响的只有"E10 与论文 A1 的绝对阈值对比"，
而那不是 E10 要回答的问题。

若要彻底消除：给 latin 加一个 `pad_to` 参数，把 vocab 补到固定值
（如 197），用未使用的 id 填坑。当前未做，因为会引入新的 padding token
语义问题，得不偿失。

## 8. 顺带解决 codex 指出的 S2 第二个混淆

`CORRECTION_alien是id位置假象.md` 追加了一节，指出我的 S2 结论
（`03_S2置换检验结果.md`）有第二个混淆：

| 数据 | vocab |
|---|---|
| `surface_fix.jsonl`（6 真实表面） | **169** |
| `surface_fix_null.jsonl`（2 个 null，slot 101/201） | **225** |

`model.py:97` 是 `Solver(len(vocab))`——vocab 大小决定参数量、
随机初始化、以及 head 与 embedding 的绑定形状。所以那个配对差里
**混进了模型规模差异**，不只是符号置换的效应。

**`latin.py` 天然解决这个混淆**（已实测）：

```
8 臂共用同一 names 时，vocab 全部 = 225（恒定）
slot = (arm_index + seed) mod 8  严格轮转
zh[0..7] en[1,2,3,4,5,6,7,0] relperm[6,7,0,1,2,3,4,5] ...
```

这正是 codex 建议的修正方案（"建一个包含全部 8 个臂的共享词表，
用同一个拉丁方配平id 块位置"）。

**但 S2 需要重跑才能用**——现有 `surface_fix*.jsonl` 是旧编码。
按latin 方式重跑需：8 臂 × 5 n × **8 种子**（配平要求 ≥ 臂数）= 320 runs。
已含在分片体系里吗？**没有**——`make_slices.py` 目前只切 E4/E6/E10/E1/E8。
要加 S2 需：

1. 在 `make_slices.py` 加一个"S2" 实验（8 臂 × 5 n × 8 seeds）
2. 写一个 `s2_arm.py`（用 latin 编码，8 臂跑同一基质）
3. 约 320 runs / 2.5 h

**建议优先级：低于 E4/E6/E10，但高于 E1/E8**——
因为 S2 是论文 §6.2 明确称为"承重检验"的那一条，
它的干净性直接影响论文可信度。
